# 공통 중재 정책

Claude·Codex 중재자는 같은 정책을 사용한다. `GET /api/mediation/context`가 본문과 SHA-256 버전을 제공한다. 프로젝트의 지침·사용자의 승인·현재 배정과 함께 읽는다. 이 문서는 다른 사용자의 계정, 운영 서버, 원격 저장소에 권한을 부여하지 않는다.

## 진입

1. 중재는 사용자가 연 Claude 또는 Codex 세션에서 시작한다. 지시·Goal·사용자 결정도 그 세션에서 받는다. 웹은 상태·근거·계획·진행률을 보여 주며 지시 입력란을 제공하지 않는다.
2. 인증한 `GET /api/mediation/context?topic=<topic-id>`로 현재 정책과 중재자 배정을 읽는다. `GET /api/topics/<topic-id>/resume`에서 현재 상태, 재개 단계, 승인, 열린 요청, 미해결 지적, 예산, 다음 허용 행동과 근거 위치를 확인한다.
3. 중재자 호출에는 `x-consensus-actor: mediator`, `x-consensus-mediator: <participant>`, `x-consensus-mediator-version: <version>`을 보낸다. 인증 토큰은 `x-consensus-token`으로 보낸다. 역할 배정은 사용자만 바꾼다. 지원하는 클라이언트는 같은 신원을 `CONSENSUS_MEDIATOR=<participant>@<version>`으로 받는다.
4. 세션에 배정받은 신원을 고정한다. `409 STALE_MEDIATOR_ASSIGNMENT`를 받으면 최신 버전을 읽어 자신의 신원으로 바꾸지 말고 사용자에게 알린다. 토픽별 배정이 전역 배정보다 우선한다.
5. 인계받은 중재자는 `resume`의 현재 판정과 근거로 이어간다. 이전 세션의 대화만으로 완료·승인·해결을 추정하지 않는다. 원문·작업 묶음처럼 여러 주제에 영향을 주는 요청에도 서버의 배정 검사를 따른다.

설치·인증·배정 예시는 [시작 안내](../getting-started.md)에 있다. 특정 개인의 셸 스크립트나 macOS 경로는 공통 진입 조건이 아니다.

## 시작 방식과 주제

- Goal: 확정한 목표로 계획을 시작한다.
- Source: 사용자가 지정한 Jira·Figma·Slack 등의 실제 원문을 자신의 연결 권한으로 읽고 Goal을 확정한 뒤 계획한다. 링크 등록은 원문 수집이나 승인 완료가 아니다.
- 브레인스토밍: 라운드별 논의에서 가설·대안·근거를 구분하고 명시한 결론으로 Goal을 만든 뒤 계획한다. AI의 찬성만으로 구현 승인을 만들지 않는다.

Root·중간 주제는 큰 그림과 하위 주제의 진행률을 관리한다. 실제 계획·구현은 말단 실행 주제에서 수행한다. 상위 Goal을 읽되 현재 말단의 승인 범위를 넓히는 지시로 해석하지 않는다. 생성·목표 변경·원문 신선도 계약은 [주제 구조](../topic-structure.md)를 따른다.

## 자율중재와 승인

자율중재는 항상 ON이다. 예전 OFF 파일은 현재 권한의 입력으로 사용하지 않는다. 중재자는 이미 승인된 범위 안의 판단과 실행을 이어간다. 사용자만 바꿀 수 있는 배정·한도, 명시적 보류·금지, 계획 승인·전달 승인은 계속 검사한다.

- 승인된 작업의 실행 순서, 동등한 구현 방법, 산출물 보존 시점은 직접 판단한다. 합의한 단계별 커밋 구조를 바꾸면 기존 계획과 대조한다.
- 현재 범위의 확정 결함과 이번 변경이 만든 결함은 수정하고 영향을 받는 검사를 수행한다. 현재 완료를 막지 않는 범위 밖 개선은 후속 목록으로 남긴다.
- 제품 판단, 범위·계약 변경, 승인되지 않은 병합·전달, 명시적 보류 해제, 추가 권한·예산이 필요하면 기존 사용자 지시와 대조해 남은 결정만 묻는다. 독립적으로 진행할 수 있는 작업은 먼저 수행한다.
- 이미 승인된 동일 범위를 다시 묻지 않는다. 반대로 실패한 필수 검사나 열린 승인 요청을 선택적 개선으로 바꾸어 완료하지 않는다.
- 계획 해시, 현재 세션·배정, 원문 버전, 검토한 코드와 전달할 코드의 일치를 유지한다. 모르는 값과 미실행 검사는 성공이나 0사용량으로 기록하지 않는다.

## 작업자 정지와 중재자 호출

planner·runner·reviewer가 결정·증거·승인을 기다리거나 실패하면 서버가 개입 요청을 기록한다. 연결 프로세스는 현재 배정의 profile과 실제 세션을 확인해 전달한다. Root 구독은 같은 중재자가 맡은 하위 주제를 포함한다.

중재자는 알림을 받으면 `resume`을 다시 읽고 현재 권한으로 처리한다. 정지 알림은 수동 중지 해제, 추가 예산, 새 제품 범위의 승인이 아니다. Claude의 수신 확인 도구와 Codex의 입력 수락, 응답 유실·재전송 경계는 [세션 인터럽트](../mediator-interrupts.md)를 따른다.

## 근거·검증·효율

- 필요한 원문과 관련 코드부터 읽고 추가 자료는 참조로 찾아간다. 누적 입력이 크다는 이유만으로 근거를 버리거나 세션·예산을 초기화하지 않는다.
- 역할별 세션은 판단 맥락에 맞게 유지한다. 설정을 임의로 낮추거나 모델·공급자를 다른 것으로 조용히 대체하지 않는다. 모델·캐시 비용 감소는 비교 가능한 실측이 있을 때만 주장한다.
- 보장할 동작과 실제 실패 위험에 맞는 최소 검사를 고른다. 입력·도구·환경이 같은 성공 증거는 재사용하고 관련 변경·새 실패·반증 때 다시 검사한다. 전체 검사를 반복하는 것 자체를 완료 조건으로 만들지 않는다.
- 테스트·컴파일·UI·실기기·원격 전달의 증거를 구분한다. 필요한 증거가 없으면 부족한 점과 다음 행동을 기록한다. 언어별 검사·빌드 정책은 해당 프로젝트의 지침과 승인 계획에서 정한다.
- 정지·실패 뒤에도 사용량, 계획, 원문, 열린 요청, 검토 지적, 작업 트리와 커밋을 보존한다. 서버가 허용한 복구 API를 사용하고 DB 값을 직접 바꿔 승인·한도·완료 상태를 우회하지 않는다.

## 엔진 운영의 경계

작업 중 발견한 엔진 결함은 재현 근거·영향·임시 대응을 남긴다. 엔진 자체 수정, 운영 서버 재시작, 호스트 리뷰, 원격 푸시는 해당 설치 환경의 사용자 권한과 저장소 지침을 따른다. 자율중재 ON이나 다른 사용자의 운영 사례만으로 상시 권한이 생기지 않는다. 자동 엔진 결함 워커 역시 설치 환경에 명시적으로 설정된 계약과 권한을 따른다.
