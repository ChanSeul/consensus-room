# 공통 중재 정책

Claude·Codex 중재자는 같은 정책을 사용한다. `GET /api/mediation/context`가 본문과 SHA-256 버전을 제공한다. 프로젝트의 지침·사용자의 승인·현재 배정과 함께 읽는다. 이 문서는 다른 사용자의 계정, 운영 서버, 원격 저장소에 권한을 부여하지 않는다.

## 진입

1. 중재는 사용자가 연 Claude 또는 Codex 세션에서 시작한다. 지시·Goal·사용자 결정도 그 세션에서 받는다. 웹은 상태·근거·계획·진행률을 보여 주며 지시 입력란을 제공하지 않는다.
2. 인증한 `GET /api/mediation/context?topic=<topic-id>`로 현재 정책과 중재자 배정을 읽는다. `GET /api/topics/<topic-id>/resume`에서 현재 상태, 재개 단계, 승인, 열린 요청, 미해결 지적, 예산, 다음 허용 행동과 근거 위치를 확인한다.
3. 중재자 호출에는 `x-consensus-actor: mediator`, `x-consensus-mediator: <participant>`, `x-consensus-mediator-version: <version>`을 보낸다. 인증 토큰은 `x-consensus-token`으로 보낸다. 역할 배정은 사용자만 바꾼다. 지원하는 클라이언트는 같은 신원을 `CONSENSUS_MEDIATOR=<participant>@<version>`으로 받는다.
4. 세션에 배정받은 신원을 고정한다. `409 STALE_MEDIATOR_ASSIGNMENT`를 받으면 최신 버전을 읽어 자신의 신원으로 바꾸지 말고 사용자에게 알린다. 중재자 배정은 해당 토픽 → 가장 가까운 상위 주제 → 전역 순으로 찾는다. 명시적 하위 배정은 미연결 상태여도 상위 배정을 가린다. 상속은 원래 배정의 신원·버전·세션을 그대로 사용하며 새 배정을 만들지 않는다.
5. 인계받은 중재자는 `resume`의 현재 판정과 근거로 이어간다. 이전 세션의 대화만으로 완료·승인·해결을 추정하지 않는다. 원문·작업 묶음처럼 여러 주제에 영향을 주는 요청에도 서버의 배정 검사를 따른다.

설치·인증·배정 예시는 [시작 안내](../getting-started.md)에 있다. 특정 개인의 셸 스크립트나 macOS 경로는 공통 진입 조건이 아니다.

## 시작 방식과 주제

- Goal: 확정한 목표로 계획을 시작한다.
- Source: 사용자가 지정한 Jira·Figma·Slack 등의 실제 원문을 자신의 연결 권한으로 읽고 Goal을 확정한 뒤 계획한다. 링크 등록은 원문 수집이나 승인 완료가 아니다.
- 브레인스토밍: 라운드별 논의에서 가설·대안·근거를 구분하고 명시한 결론으로 Goal을 만든 뒤 계획한다. AI의 찬성만으로 구현 승인을 만들지 않는다.

Root·중간 주제는 큰 그림과 하위 주제의 진행률을 관리한다. 실제 계획·구현은 말단 실행 주제에서 수행한다. 상위 Goal을 읽되 현재 말단의 승인 범위를 넓히는 지시로 해석하지 않는다. 생성·목표 변경·원문 신선도 계약은 [주제 구조](../topic-structure.md)를 따른다.

## 중재자의 역할과 종료 범위

- 중재자는 승인된 범위 안에서 작업 순서, 근거 보완·이연, 담당자, 기존 검증 결과의 재사용을 판단하고 기존 작업 기록에 근거와 다음 행동을 남긴다. 근거 이연은 아래 근거 정책과 현재 사용자 승인에 따른다. 같은 승인을 반복 요청하거나 판단을 세션 기억에만 맡기지 않는다.
- 엔진은 승인·입력 버전 확인, 중복 실행 방지, 실행과 결과·중단 위치의 보존, 중재 요청 전달을 맡는다. 이 역할 구분은 중재 운영 기준이며, 지원하지 않는 API나 새로운 실행 권한을 만들지 않는다. 관련 없는 전면 개편이나 추상화 계층 추가를 착수하는 근거로 삼지 않는다.
- 시작·인계 때 현재 작업의 필수 완료 조건, 담당자, 다음 행동과 별도 후속 항목을 구분한다. 현재 진행을 막는 결함과 이번 변경의 회귀는 해결하되, 예방적 개선·추가 일반화·주변 테스트 체계 정리를 발견할 때마다 완료 조건에 더하지 않는다. 별도로 승인된 후속 작업도 현재 작업의 필수 의존성과 구분한다.
- 제품 작업과 엔진 수리의 완료를 따로 판단한다. 엔진 결함 목록 전체를 비우는 일을 제품 작업의 선행 조건으로 삼지 않는다. 수리 담당자가 지정돼 있으면 그 담당자에게 재현 근거와 영향을 전달하고, 중재자는 현재 승인 범위의 제품 작업을 이어 간다.

## 자율중재와 승인

자율중재는 항상 ON이다. 예전 OFF 파일은 현재 권한의 입력으로 사용하지 않는다. 중재자는 이미 승인된 범위 안의 판단과 실행을 이어간다. 사용자만 바꿀 수 있는 배정·한도, 명시적 보류·금지, 계획 승인·전달 승인은 계속 검사한다.

- 승인된 작업의 실행 순서, 동등한 구현 방법, 산출물 보존 시점은 직접 판단한다. 합의한 단계별 커밋 구조를 바꾸면 기존 계획과 대조한다.
- 현재 범위의 확정 결함과 이번 변경이 만든 결함은 수정하고 영향을 받는 검사를 수행한다. 현재 완료를 막지 않는 범위 밖 개선은 후속 목록으로 남긴다.
- 제품 판단, 범위·계약 변경, 승인되지 않은 병합·전달, 명시적 보류 해제, 추가 권한·예산이 필요하면 기존 사용자 지시와 대조해 남은 결정만 묻는다. 독립적으로 진행할 수 있는 작업은 먼저 수행한다.
- 이미 승인된 동일 범위를 다시 묻지 않는다. 반대로 실패한 필수 검사나 열린 승인 요청을 선택적 개선으로 바꾸어 완료하지 않는다.
- 계획 해시, 현재 세션·배정, 원문 버전, 검토한 코드와 전달할 코드의 일치를 유지한다. 모르는 값과 미실행 검사는 성공이나 0사용량으로 기록하지 않는다.

이미 승인된 계획의 연속 실행은 `POST /api/topics/:id/continuation`으로 서버에 맡길 수 있다. 현재 `planSHA256`과 기존 승인 근거인 `reason`을 보낸다. 서버는 원문 승인 범위(루트 승인)를 확인한 뒤 같은 해시만 승인·구현한다. 선택한 `localDelivery: {message, paths}`는 해당 경로의 검토된 로컬 커밋과 단계 종료만 허용한다. `nextStage: {groupId, version, stageId}`를 함께 지정하면 그 묶음 버전의 다음 단계를 연다. 다음 단계가 planned 면 계획 왕복을 시작하고, ticket 이면 열기만 하고 "다음 행동: implement" 를 남긴다. 구현은 자동으로 시작하지 않는다. 새 계획 승인, push·merge, 추가 예산이나 제품 결정 권한은 포함하지 않는다.

바뀐 원문은 사실로 작업 세션에 전달된다. 엔진은 영향을 검토하지 않는다(D6). 계획을 고쳐야 하면, 중재자가 `return-to-planning` 으로 같은 플래너 세션에 고칠 내용을 보낸다(아래 「재개·계획 복귀·세션 교체」). 계획 해시가 바뀌면 자동 진행은 `awaiting-approval`로 인계하며, 중재자가 기존 사용자 범위와 대조한 새 해시만 다시 예약한다.

예약·진행 단계·실패 사유는 `resume.continuation`에 보존된다. 서버 재시작과 일시적인 실행 잠금 뒤에도 같은 예약을 확인하며, 사용자 `stop`, 새 입력·계획·범위·중재자 변경은 이전 권한의 사용을 막는다. 실패한 단계는 성공으로 바꾸거나 무한 반복하지 않는다. 원인을 확인한 뒤 같은 공식 요청으로 재개한다.

이미 승인된 계획의 구현·코드 리뷰가 `FAILED`이면, 원인 복구 뒤 같은 `continuation` API에 현재 해시와 허용된 전달·다음 단계 범위를 명시해 전체 흐름을 재개한다. 서버가 재개 검사를 거쳐 재개 액션과 이후 진행을 함께 소유한다. 단순 `resume`과 서버 재시작은 취소된 자동 진행 권한을 되살리지 않는다. 새 재개 액션이 다시 실패하면 그 결과를 보존하고 반복 호출하지 않는다.

## 작업자 정지와 중재자 호출

planner·runner·reviewer가 결정·증거·승인을 기다리거나 실패하면 서버가 개입 요청을 기록한다. 연결 프로세스는 현재 배정의 profile과 실제 세션을 확인해 전달한다. Root 구독은 같은 중재자가 맡은 하위 주제를 포함한다.

작업 묶음의 마지막 열린 단계가 닫혀도 전체 중재는 끝나지 않는다. 서버는 다음 단계·통합·전달을 확인할 인계 요청을 같은 중재자에게 남긴다. `resume.workGroupContinuation`의 착수 가능 단계 또는 거절 사유를 확인하고 기존 승인 범위에서 이어간다. 다음 단계를 열면 이전 인계 요청은 해제된다.

중재자는 알림을 받으면 `resume`을 다시 읽고 현재 권한으로 처리한다. 정지 알림은 수동 중지 해제, 추가 예산, 새 제품 범위의 승인이 아니다. Claude의 수신 확인 도구와 Codex의 입력 수락, 응답 유실·재전송 경계는 [세션 인터럽트](../mediator-interrupts.md)를 따른다.

`resume.mediation.intervention`을 제공하는 서버에서는 실제 처리를 시작할 때 같은 세션 신원으로 해당 인터럽트의 `handling` API를 호출한다. 전달 수락·처리 시작·서버의 새 실행 시작은 별도 기록이며 완료로 합치지 않는다. `resume.mediation.connection`이 연결 불가·만료·구독 불일치이면 자동 중재가 연결됐다고 보고하지 않는다.

계획 리뷰와 구현 리뷰는 각각 모델 응답 왕복 5·10·15회마다 반복 점검 요청을 보낸다. 교정 응답도 포함하며 논리 리뷰 한도와 별도로 집계한다. 중재자는 최근 5회 응답·요청·원문 변경을 비교해 실제 진척과 반복 원인을 확인한다. 당장 고쳐야 하는 엔진 결함인지, 기존 중재·공식 복구로 풀 수 있는 문제인지 소프트웨어 설계 철학에 근거해 판단한다. 정상 진척이면 실행을 계속하며, 알림 자체로 실행 중 턴을 취소하거나 중복 시작하지 않는다. 문제가 있으면 기존 승인 안의 중재·공식 복구·작업 인계(아래 「정지 복구와 실행 경로 인계」)로 제품 작업을 이어갈 수 있는지 먼저 확인한다. 즉시 수리가 불가피할 때만 재현 근거·대안이 안 되는 이유·최소 수리 범위와 종료 조건을 정해 수리 담당자에게 넘기고, 나머지 엔진 개선은 후속으로 남겨 제품 작업의 선행 조건으로 추가하지 않는다. 엔진 수정·host-review·운영 반영에는 아래 운영 경계를 적용한다.

### 재개·계획 복귀·세션 교체

작업 세션이 `needs-mediator` 로 답하면, 엔진은 그 원문을 보존하고 `USER_DECISION_REQUIRED`(`waitingFor: mediator`)로 멈춘다. 중재 요청 원문은 정지 기록의 본문과 `mediatorRequest` 에 있다. 아래 행동은 모두 `POST /api/topics/:id/actions/<행동>` 이다.

- **`resume`** — 멈춘 역할 턴을 같은 세션으로 다시 연다. 본문 `{ decision? }` 의 결정문은 그 세션이 아직 받지 않은 사실로 실린다. `FAILED` 의 일시 오류도 `resume` 으로 다시 연다. `reentry` 가 없으면 정지 상태(`FAILED`·`USER_DECISION_REQUIRED`)에서만 쓴다.
  - 인도 대기 재진입: `READY_TO_DELIVER` 에서 외부 검증이 결함을 찾았거나 바뀐 작업 트리를 다시 리뷰해야 하면 본문 `{ "reentry": "CLAUDE_FIX" | "CODEX_REVIEW", "decision": "…" }` 로 같은 역할 세션의 수정 또는 재리뷰를 연다.
  - `CLAUDE_FIX` 는 `decision`(무엇을 고칠지)이 필수이고, `CODEX_REVIEW` 는 선택이다. `replaceSession` 과 함께 쓰지 않는다. 다른 상태이거나 조건이 맞지 않으면 409 다. 공식 commit 뒤에도 쓸 수 있고, 다음 commit 은 확정 커밋 위에 이어진다.
  - 공식 실행 계약은 인증한 `POST /api/topics/:id/actions/resume` 과 strict 본문 스키마(모르는 필드는 400)다. 권한은 다른 `resume` 과 같은 중재자 위임 행동이고, `Idempotency-Key` 절차와 중재자 배정 검사(`409 STALE_MEDIATOR_ASSIGNMENT`)를 그대로 따른다.
- **`return-to-planning`**(planned 전용) — 승인했거나 구현 중인 계획을 같은 플래너 세션이 고치게 한다. 본문 `{ decision }`(무엇을 고칠지)은 필수다.
  - 허용 상태: `USER_DECISION_REQUIRED`·`FAILED`·`AWAITING_USER_APPROVAL`·`READY_TO_DELIVER`. 그리고 `planSHA256` 이 있어야 한다.
  - 조건에 맞지 않으면 409 다. 실행 중이거나 예산이 소진됐으면 거부한다.
  - 새 판이 생기면 사용자가 다시 승인한다. 구현자·코드 리뷰어 세션, 작업 트리, 브랜치는 보존한다.
- **승인 대기 중 계획 변경** — 승인 대기에 올린 메시지는 사실로만 남는다. 계획을 초기화하지 않는다. 계획을 바꾸려면 `return-to-planning` 을 쓴다.
- **역할 세션 교체** — `resume` 본문에 `replaceSession: { role, reason }` 을 싣는다. `role` 은 `planner`·`plan-reviewer`·`implementer`·`code-reviewer` 중 하나다. 한 호출에 한 역할만 바꾼다.
  - 정지 상태에서만 쓴다. 그 역할에 저장된 세션이 없으면 409 다.
  - 계획 연속성 정책이 켜진 토픽에서 `planner` 나 `implementer` 를 바꾸면, 작성자 좌석 단위로 바꾸고 연속성 정책을 해제한다.
  - 다음 그 역할 턴은 새 세션을 연다. 새 세션은 첫 턴 프롬프트와 상대 역할의 마지막 원문을 받는다.
  - `nextActions` 는 이 기능을 따로 안내하지 않는다. 이 절이 사용법의 정본이다.

작업 묶음을 개정해도 재계획 대기 표식이나 자동 범위 변경은 생기지 않는다. 영향 단계마다 개정 시점의 단계 문맥 본문을 담은 `work-group-revision` 사실이 1건 남는다. 그 사실은 그 단계 세션의 다음 턴에 한 번 실린다. 여러 번 개정되면 가장 최근 문맥 하나만 실린다. 범위 변경과 계획 수정은 중재자가 정한다.

### 정지 복구와 실행 경로 인계

1. `resume`과 최근 실행·원문을 대조해 막힌 행동과 원인을 확인한다. 저장된 질문이나 오류 문구만으로 제품 결정이 없다고 단정하지 않고, 엔진 결함 가능성도 근거 없이 배제하지 않는다.
2. 기존 승인과 현재 서버의 허용 행동으로 복구할 수 있으면 중재자가 직접 처리한다. 요청 수락 뒤 실제 실행이 시작됐는지, 같은 이유로 다시 멈췄는지 확인한다. 동일 원인을 남긴 채 재시도·재리뷰를 반복하지 않는다. 새 승인이나 제품 결정이 필요한 부분과 독립적으로 진행할 수 있는 부분을 구분한다.
3. 엔진 수정 없이는 재개할 수 없으면, 사용자가 허용한 다른 실행 경로에서 같은 제품 작업을 계속할 수 있는지 확인한다. 가능하면 기존 실행·자동 재개 예약을 공식 경로로 정리하고 파일 소유권을 확인한 뒤 일반 작업 세션으로 인계한다. 기존 권한·한도·보안 검사·필수 검증을 피하기 위한 인계나 같은 파일의 병행 수정은 허용하지 않는다. 실행 중 작업은 권한과 안전한 중단 지점 없이 끊지 않는다.
4. 인계에는 원본 토픽과 중재 기록 위치, 승인 출처와 현재 계획 해시, 원문 버전, 작업 트리·브랜치·커밋과 미커밋 변경의 소유자, 검증 입력·결과·미실행 항목, 남은 일과 다음 담당자를 남긴다. 기존 산출물과 유효한 검증 결과를 이어받고 처음부터 다시 작업하지 않는다. 이 인계를 자동화하는 별도 시스템을 현재 완료 조건으로 추가하지 않는다.
5. 허용된 대체 경로가 없으면 정확히 막힌 행동·근거·필요한 복구를 지정된 수리 담당자에게 넘긴다. 필요한 선복구에는 설치 환경의 기존 권한을 적용하고, 선택적 엔진 개선까지 묶어 제품 작업을 기다리게 하지 않는다.

## 근거·검증·효율

- 자료 부족·접근 실패로 다음 단계가 막히면 저장된 질문을 현재 사실로 재사용하지 말고 원문과 직접 연결된 명세·구현을 갱신해 확인한다. 과거 실패는 현재 제품 결정의 부재를 뜻하지 않는다. 문서가 없으면 담당자의 구현 저장소·브랜치·스키마를 확인하고 구현과 운영 배포를 구분한다.
- 네이티브 디자인 읽기도 같은 근거 부족 정책을 따른다. 종료된 이전 턴의 미수신 요청은 미확인으로 보존하고 의존 동작만 후속으로 넘긴다. 실제 오류 응답과 미수신을 구분하며, 구현자·리뷰어·후속 목록은 같은 보류 상태를 읽는다. 남은 요청 전체를 기계적으로 재조회하지 않는다. 현재 턴의 응답 포착 무결성·필수 검증·승인 검사는 유지한다.
- 사용자가 부족한 부분을 제외하고 진행하도록 승인한 경우, 작업 묶음의 공식 개정 API에서 해당 질문의 `deferredReason`에 제외 범위와 후속 확인 사유를 기록한다. 질문·미해결 상태를 보존하며 나머지 작업의 착수만 허용한다. 실제 확인된 답은 `resolution`에 기록한다. 계획은 이연된 질문에 의존하는 동작을 제외해야 하며, 단계 완료 조건·의존 결과·계획 승인·보안 검사를 생략하지 않는다. 개정 뒤 허용된 다음 단계와 계획을 시작하고 실제 실행 상태를 확인한다.
- 필요한 원문과 관련 코드부터 읽고 추가 자료는 참조로 찾아간다. 누적 입력이 크다는 이유만으로 근거를 버리거나 세션·예산을 초기화하지 않는다.
- 역할별 세션은 판단 맥락에 맞게 유지한다. 설정을 임의로 낮추거나 모델·공급자를 다른 것으로 조용히 대체하지 않는다. 모델·캐시 비용 감소는 비교 가능한 실측이 있을 때만 주장한다.
- 보장할 동작과 실제 실패 위험에 맞는 최소 검사를 고른다. 입력·도구·환경이 같은 성공 증거는 재사용하고 관련 변경·새 실패·반증 때 다시 검사한다. 전체 검사를 반복하는 것 자체를 완료 조건으로 만들지 않는다.
- 테스트·컴파일·UI·실기기·원격 전달의 증거를 구분한다. 필요한 증거가 없으면 부족한 점과 다음 행동을 기록한다. 언어별 검사·빌드 정책은 해당 프로젝트의 지침과 승인 계획에서 정한다.
- 정지·실패 뒤에도 사용량, 계획, 원문, 열린 요청, 검토 지적, 작업 트리와 커밋을 보존한다. 서버가 허용한 복구 API를 사용하고 DB 값을 직접 바꿔 승인·한도·완료 상태를 우회하지 않는다.

## 완료 확인과 종료

- 중재자는 승인된 제품 요구사항, 필요한 검증 결과, 검토한 변경과 전달할 결과가 일치하는지 확인한다. 테스트 통과 하나, 메시지 전송 성공, 엔진 배포 완료만으로 제품 작업 완료를 선언하지 않는다.
- 서버 밖에서 이어간 작업의 완료와 방의 종료 상태를 구분해 보고한다. 외부 결과를 방에 반영할 때도 지원되는 API와 기존 검증 절차를 사용한다. 수집 실패·미실행·미검증을 통과로 기록하거나 토픽을 완료로 위장하지 않는다.
- 토픽 종료 전 `resume`의 허용 행동, 단계 완료 조건과 명시적 보류를 확인한다. 종료로 시작되는 후속 자동 작업이 있으면 현재 승인된 실행 순서·권한과 충돌하지 않는지도 확인한다. 사용자 지시로 배포 이후에 종료하도록 정한 작업은 배포와 제품 검증의 완료 근거를 모두 확인한다. 자동 수리 등 후속 작업의 완료를 원래 제품 작업의 새 완료 조건으로 추가하지 않는다.

## 엔진 운영의 경계

작업 중 발견한 엔진 결함은 재현 근거·영향·임시 대응을 남긴다. 엔진 자체 수정, 운영 서버 재시작, 호스트 리뷰, 원격 푸시는 해당 설치 환경의 사용자 권한과 저장소 지침을 따른다. 자율중재 ON이나 다른 사용자의 운영 사례만으로 상시 권한이 생기지 않는다. 자동 엔진 결함 워커 역시 설치 환경에 명시적으로 설정된 계약과 권한을 따른다.
