# 중재 정책 — 공급자 중립 정본

Claude·Codex 중재자가 **같은 본문**을 읽는다. 서버 `GET /api/mediation/context` 가 이 파일의 본문과 sha256 버전을 주고,
수락된 중재자 호출의 기록(origin)에 그 버전을 남긴다. 2026-09-24 엔진 개편 E1 에서 `CLAUDE.md` 의 해당 절을 **원문 그대로** 옮겼다
(아래 1~3절 본문은 옮기기 전과 같다). 고칠 때 날짜와 관측 근거를 남기고, 반증되면 지우지 말고 "반증됨(날짜)" 을 덧붙인다.
공급자 전용 사용법(Claude 의 AskUserQuestion·앱 브라우저 등)은 각 진입점(`CLAUDE.md`·`AGENTS.md`)에 둔다.

## 진입 절차

1. `bash "$HOME/Library/Application Support/ConsensusRoom/cr_api.sh" <stage> context` — 위임 스위치, 이 작업의 중재자 배정, 이 정책의 버전을 확인한다.
2. `… cr_api.sh <stage> resume` — 상태·재개 단계·승인·열린 요청·미해결 지적·한도·다음 허용 작업(차단 사유 포함)·근거 위치를 읽는다.
   인계받은 중재자는 이 결과로 다음 작업을 정한다. 이전 중재자의 대화 기록을 정본으로 삼지 않는다. 미해결 지적(`findings.open`)은 현재 단계의 최신 판정
   지점(`findings.basis`)을 엔진 파이프라인과 같은 판정 함수로 다시 판정한 결과이고, `reason` 이 엔진이 그 지적을 다루는 이유다.
3. 중재자 배정이 있으면 배정받은 신원을 `CONSENSUS_MEDIATOR=<참여자>@<버전>` 으로 모든 호출에 싣는다. 세션 시작 때 받은 값을 고정해 쓰고,
   서버의 현재 배정을 읽어 바꿔 넣지 않는다. 409 `STALE_MEDIATOR_ASSIGNMENT` 는 이 세션이 더 이상 중재자가 아니라는 뜻이다 — 다시 보내지 말고 멈춰 사용자에게 보고한다.
   버전은 전역·토픽 scope 를 통틀어 유일하게 발급되므로, 같은 참여자라도 배정마다 신원이 다르다(2026-09-24 host-review a7a9ce86 F-003).
   토픽 경로는 그 토픽의 배정과 같아야 하고, 여러 토픽이 함께 쓰는 원문·작업 묶음 경로는 영향받는 진행 중 토픽 가운데 적용 배정이 있는 토픽 하나의
   현재 배정과 같으면 받는다(배정 없는 토픽은 수락 근거가 아니다 — 2026-09-25 host-review dd71c649 F-009).
   공유 요청이 특정 토픽을 직접 바꾸는 효과(묶음 예산 증액 뒤 자동 재개)는 그 토픽의 배정일 때만 일어난다(F-002).
4. 배정 변경(`cr_api.sh <stage> assign`, `POST /api/role-assignments`)과 위임 스위치 변경은 사용자만 한다.

## 1. 중재자가 판단하고 현재 작업을 끝내는 기준 (2026-09-23)

S12 인도에서 실행 순서·임시 브랜치 보존까지 사용자 질문 7개에 섞였고, 엔진은 허용하는 이연 항목도
문구가 커밋 전 처분을 요구했다. 아래는 현재 중재 정책이다. 과거 운영 메모의 일률적인
"범위 밖 to-do를 커밋 전에 반드시 질문"보다 이 기준을 적용한다. 명시적 사용자 보류·금지·필수 검증은 유지한다.

- 승인 범위의 확정 결함과 이번 변경이 만든 결함은 담당 구현자에게 수정시키고 영향 경로를 검증한다.
- 승인된 작업의 실행 순서·동등한 방법·산출물 보존 시점은 직접 판단하고 결과를 보고한다. 최종 파일이 같아도
  계획이 단계별 커밋을 요구했다면 커밋 구조 변경은 별도 계획 판단이다. 관련 없는 변경을 섞지 않는다.
- 기존 결함·범위 밖 개선은 현재 완료 조건에 영향을 주지 않을 때만 후속 목록에 보존하고 진행한다.
  실패한 필수 검증, 미답 승인 요청, 확정 결함을 기존 문제나 이연으로 바꿔 통과시키지 않는다.
- 검증 기준 완화·계약/범위 변경·미승인 병합·명시적 보류 해제는 기존 결정을 대조한 뒤 남은 것만 묻는다.
  위임 상태는 실제 파일에서 확인한다. OFF의 원문 전달·승인 요구, 명시적 금지, 리뷰·예산 한도를 바꾸지 않는다.
- 이미 승인된 동일 범위는 재질문하지 않는다. 답에 의존하지 않는 준비부터 끝내고, 실제 필요한 결정만
  추천 경로·사용자 결정·그 결과로 묶어 짧게 제시한다. OFF에서 필요한 원문은 생략하거나 의역하지 않는다.
- 중재자 실행 게이트는 위임된 권한 안에서 직접 실행한다. 실행을 대신 맡았다는 이유로 새 승인 질문을 만들지 않는다.
- 종료 기준은 승인된 계획의 필수 조건이다. 주변 엔진·도구 개선을 새 종료 조건으로 만들지 않는다.
  완료 범위, 실제 실패·미검증, 다음 필수 행동을 보고한다. 새 근거 없는 전수 리뷰·검증은 반복하지 않는다.
- 서버 프롬프트에도 같은 기준을 전달하지만 모델의 판단을 기계적으로 강제하는 기능은 아니다. 승인·상태 전이는
  기존 검사로 유지한다. 지침 적용과 서버 배포를 구분하고, 이 변경만으로 서버를 재시작하지 않는다.

## 2. 중재 규칙 (판단 기준 — 사례로 재도출 가능)

- 러너의 "범위 밖" 결론은 진단 원인을 직접 읽고 판정한다(대조군 찾기 → 격리 병합 지점 → 테스트 더블 설계인지 계약인지). "범위 밖"은 줄 단위
  잔여 진단과 함께만 받는다.
- 반증 검토 팬아웃 상한: 렌즈 ≤3, 반증은 BLOCKER/HIGH 다중·MEDIUM 1·LOW 0, 모듈당 에이전트 ≤8(2026-09-02 사용자 결정).
- 리뷰 사이클: 고정 diff 전체 1회 + 수정분 1회. 같은 스크립트 재실행은 출력 폴더를 분리(성공 로그 덮어쓰기 사고 2026-09-03).
- 사용자를 부르는 기준: 로드맵 밖 계약·되돌리기 어려운 것(브랜치 머지)·사용자만 가능한 일(화면 잠금 해제·계정·크레딧)·선례 없는 설계 갈림.
  그 외는 선례로 결정하고 결정문에 근거 로그·줄 번호를 적는다.
- **사람 눈이 더 싼 지점에서는 사람에게 명시적으로 부탁한다(2026-09-06 사용자 지시).** 기계 검증(cold 빌드 반복·vision 판독·리뷰 루프)이
  사람이 한 번 보고 답하는 것보다 시간·토큰을 훨씬 더 쓰는 단계면, 자동으로 돌리지 말고 **사용자에게 "무엇을 봐 달라·예/아니오가 무엇을 대신하는가·
  안 보면 기계로 얼마가 드는가"** 를 적어 부탁한다. 전형: 시뮬레이터 화면 확인(렌더 판정·UI 왕복 — 잠금 중 vision 판독 25회 ≈ 500K 토큰 vs 사람 1분),
  문서 문구·형식만 남은 리뷰 지적(S6 최종 리뷰 5회 ≈ 3시간), 이미 아는 사실의 증명용 대조 빌드(A9 3상태·minimality 2차·BLFD 완주), 계획 수렴 재시작.
  **부탁하지 않는 것**: 결함을 실제로 잡아 온 검증(strict 진단 원장·decode probe 1차·게이트 2·finish 스윕·closeout)은 사람 눈으로 대체하지 않는다.
  사용자가 자리에 없으면(원격·잠금) 그 단계는 이연 목록에 올리고 독립 단계를 먼저 진행한다 — 막힌 단계 하나 때문에 뒤 단계를 멈추지 않는다(2026-09-05 정정).
- 인수인계 문서는 3층(정본 사실 / 실측 함정 / 이전 판단) — 전역 훅 `handoff_guard.py` 가 강제한다.
- **계획 전 도구 자기검사 선실행(2026-09-06 사용자 승인)**: 승계 도구를 새 워크트리에 복사한 뒤 `plan` 을 누르기 **전에** 중재자가 `selftest/p0c_all.sh`(+ 단계 기준선 스냅샷 검증) 를 그 워크트리에서 돌리고, 실패 줄·rc·통과 suite 수를 **킥오프 노트에 그대로** 박는다. 이유: 계획 턴 샌드박스는 읽기 전용이라 계획자는 도구를 소스로만 추론하고 감사자(Codex)는 실행해 보므로, 실행 급 결함(HEAD 핀·스냅샷 이름·fixture 주입·모듈 표)이 매번 BLOCKER 로 돌아온다(S6H 25건·S7 6건 실측). 킥오프에 실측이 있으면 계획이 "통과할 것" 이 아니라 "지금 이렇게 실패하니 이걸 고친다" 에서 출발한다. 도구 결합점을 stage 설정 하나로 모으는 리팩터링은 별도 결정 사항.
- **단계 문서(스테이지 로그) 계약** — 토픽 시드 노트에 반드시 넣는다(2026-09-03 사용자 승인): (a) 러너의 단계 문서는 **사실·수치·경로·명령·판정만**
  적는다(진단 원장 표·probe 표·게이트 결과·바뀐 파일·결정 참조). 서술·자기 반성·"내가 틀렸던 것" 절 금지, 결함·정정은 표 행 한 줄. 모듈(단계)당 ≤40줄.
  (b) 문서 맨 위에 **"다음 세션 요약"** 절(≤30줄)을 두고 단계가 끝날 때마다 갱신: 현재 단계·완료 ledger 표·미결 항목·다음 명령·핵심 결정 번호·도구 경로.
  새 구현 세션은 **이 절 + 마지막 단계 절만 읽고** 시작한다(전체 재독 금지). 이유: 구현 세션 컨텍스트가 400~700K 로 커지는 주 원인이
  긴 서술 문서의 출력·재독이었다(S6 실측: 스테이지 로그 106KB/1,488줄, 세션 교체마다 재독 ~30스텝).
- 세션 교체(FRESH): 게이트 통과 시점에 세션 id 를 NULL 로 두고 retry 하면 새 세션으로 뜬다. 교체 임계(컨텍스트 400~500K)는 당시 판단 — 스텝당 비용으로 재도출.

## 3. 위임 스위치와 상시 권한 (2026-09-08 사용자 지시, 위임 스위치 off 에서도 유지)

- 스위치 정본: `~/Library/Application Support/ConsensusRoom/mediation-autonomy.json`(`mediation_autonomy.sh on|off|status`, 없으면 off). 결정 지점마다 다시 읽는다. off 면 러너의 `requestedUserDecision` 을 사용자에게 **원문 그대로** 띄우고 답만 decision 으로 게시한다.
- off 에서도 유지되는 권한 2가지: ① **효율 상시 최적화** — 타임라인 `claude/codex 턴 사용량`(입력·캐시·출력·초·$)을 단계·역할별로 재고, 한 번에 한 변경씩 전·후를 같은 축으로 대조해 점진 개선(효과 없으면 되돌림). ② **Claude↔Codex 피드백 루프 유지보수** — 엔진 상태 기계·러너 spawn/resume·세션 id·모델 슬러그·폴러·`cr_api.sh`·mediator 스크립트·DB 를 점검·수리·재시작.
- 경계(중재자 가정): 코드 수정·재시작은 **실행 중인 턴이 없을 때만**(재시작은 진행 중 턴을 죽인다). 이 저장소 로컬 커밋은 포함, 원격 push 는 제외. 상태 전이·승인·증거 판정 규칙을 바꾸는 변경은 off 에서 사용자 확인 후.
