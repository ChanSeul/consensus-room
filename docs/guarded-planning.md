# 계획 입력을 제한하고 중간 결과에서 이어가기

계획 작성·개정·감사·종결 검토에 선택적으로 적용하는 서버 제어 조사 방식이다. 구현 모델과 추론 설정은 바꾸지 않는다. 기존 토픽에는 자동 적용하지 않는다. 새 일반 토픽은 기본으로 켠 채 만든다(아래, E5 P0-1).

인증된 `POST /api/topics/:id/planning-control`로 실행 중이 아닌 토픽에 적용한다. 기존 멱등성 키와 중재자 권한 검사를 사용한다. 새 일반 토픽은 기본으로 계획 제어를 켠 채 만든다(E5 P0-1). `CONSENSUS_ROOM_GUARDED_PLANNING=0`일 때만 끄고, 그 밖의 값이나 미설정은 켬이다. 이 설정은 **이후 생성하는** 토픽에만 적용한다 — 이미 있는 토픽의 정책은 바꾸지 않는다(자동 이관 없음). 운영 토픽의 예산·리뷰·재작성 한도는 이 설정으로 늘어나거나 초기화되지 않는다. 예산을 소진한 토픽의 실사용 검증은 추가 예산 승인 후 별도로 진행한다.

작업 묶음의 새 단계 토픽은 예외다(E4 2차 보완 F012). `POST /api/work-groups/:id/next`가 단계 토픽을 만드는 transaction 안에서 계획 제어를 켜므로(이력 없는 DRAFT 라 v2), 설정·수동 `planning-control` 호출과 무관하게 v2 로 시작한다. 선행 단계에서 이어받는 결정 원문(승계 결정 이벤트)이 타임라인 참조로 실려 끝까지 읽혀야 하고, 참조 전달은 계획 제어 턴에만 켜지기 때문이다. 명시적 opt-out(`CONSENSUS_ROOM_GUARDED_PLANNING=0`)은 일반 토픽에만 적용된다.

이연 쟁점 목록(계획·감사 프롬프트)은 근거를 자르지 않는다. 목록 전체(근거 전문)가 인라인 예산(`DEFERRED_FINDINGS_INLINE_BYTES`, 8 KiB) 안이면 전문을 싣는다. 넘으면 예산 안까지의 색인(ID·심각도·제목·출처·토픽)과 남은 건수를 싣고, 근거 전문은 엔진이 그 턴 전에 쓴 원문 산출물(`deferred-findings-digest`, 내용이 같으면 새 판 없음)을 참조로 읽게 한다. 계획 제어 턴은 그 경로를 `readablePaths` 로 받아 `kind=artifact selector=<경로>` 문서로 싣고 모델은 offset 0 부터 `nextOffset` 이 null 이 될 때까지 읽는다. 계획 제어가 없는 턴은 같은 경로의 파일을 읽는다. 모든 항목은 전문·색인·남은 건수 중 하나로 드러난다. 작업 묶음 단계 문맥의 결과 줄도 요약만 싣는다 — 보류 지적은 ID 목록·개수, 넘긴 결정은 개수·요약 해시(정렬한 `{topicId, sequence, sha256}` 목록의 정본 JSON sha256). 원문은 위 이연 목록과 승계 결정 이벤트로 간다. 결과 줄에 전문을 실으면 결과 수에 비례해 커져 계획 제어 패킷 상한(계획 64 KiB·감사 96 KiB)을 넘는다.

## 모델이 받는 내용

모델은 필수 지시문과 작업 계약, 짧은 중간 결과, 서버가 허용한 자료 조각을 받는다. 파일·검색·캐시된 외부 근거·메모리·이미지를 읽으려면 `planningStep.requests`로 종류, 선택자, 질문, 바이트 위치를 반환한다. 서버가 Git 스냅샷이나 이미 저장된 외부 근거에서 자료를 가져온다. 진단 원문처럼 엔진이 허용한 작업 트리 밖의 파일도 `artifact` 자료로 등록해 해시를 확인하고 분할 전달한다. 이 경로에서 Slack·Jira·Figma 원문을 다시 수집하지 않는다. 외부 근거의 갱신은 기존 evidence 기능이 담당한다.

| 항목 | 제한 |
| --- | --- |
| Claude 계획·개정의 최종 조립 텍스트 입력 | UTF-8 64 KiB |
| Codex 계획 감사·종결 검토의 최종 조립 텍스트 입력 | UTF-8 96 KiB |
| 같은 세션의 누적 호스트 입력·응답 | 측정값만 남긴다(체크포인트 `context`). 다음 호출을 막지 않는다 |
| 직렬화한 자료 조각 | 8 KiB |
| 한 회차 자료 묶음 | 24 KiB |
| 중간 결과 | 12 KiB |
| 회차별 읽기 요청 | 4개 |
| 조사 회차 | 측정값만 남긴다(진행 표시·예산 환급). 회차 수만으로 최종 정리를 강제하지 않는다(E3-4a) |
| 이미지 | 회차당 PNG 1개, 5 MiB 이하 |

텍스트 한도는 CLI 어댑터가 필수 지시문을 붙인 뒤 다시 검사한다. 필수 계약이 넘치면 내용을 잘라 보내지 않고 중간 결과를 남겨 멈춘다. 이미지 바이트는 텍스트와 따로 기록한다. 이 수치는 모델 전체 문맥 한도나 토큰 수를 뜻하지 않는다. CLI 자체 지시문과 공급자 내부 처리는 별도다.

Claude는 첫 계획에서 생성하거나 연결한 세션을 조사·개정·구현·수정까지 이어 쓴다. 승인 계획의 해시·범위·계획 세대와 작성 세션 ID를 함께 저장하고, 첫 구현에서 이 연결을 확인한다. 구현 시작에는 승인 지시와 이후 변경분만 전달하며, 이미 작성한 계획 전문과 전달한 자료 조각을 반복 삽입하지 않는다. 읽은 자료 목록은 같은 세션의 단계 전환을 넘어 보존하고, 현재 스냅샷에서도 내용이 같은 자료만 인용과 중복 제거에 사용한다. 계획 개정에 정확한 행 번호가 필요하거나 문맥 압축으로 세부 내용을 잃었을 때만 저장된 원문을 조회한다. 압축으로 잃은 자료 조각은 `rereadReason`을 명시한 요청으로만 제한 내에서 다시 제공하며 새 근거로 집계하지 않는다. 연결 불일치(짝 없는 세션 id 변경·승인 바인딩과 다른 구현 세션)에서는 새 세션을 만들지 않고 중재를 기다린다. 관측된 세션 유실·문맥 초과는 아래 "세션 복구"의 작성자 좌석 절차로 한 번 복구한다. 실행 이력·저장 응답이 없는 토픽에서 계획 작성 전에 활성화한 정책 2에만 연속 세션을 적용한다. 이미 정책 1을 쓰던 토픽과 계획 승인 후 활성화한 토픽은 기존 세션 방식을 유지한다. 허용 오차를 개정하면 기존 세션 연결을 확인한 뒤 계획·승인 해시와 같은 트랜잭션에서 갱신하고, 변경된 허용 오차를 다음 턴에 전달한다. Codex 검토는 기존 세션을 이어가고 이미 전달한 동일 조각을 다시 싣지 않는다. 같은 세션의 누적 호스트 입력·응답은 측정값으로만 남기고, 그 크기나 측정 기록이 없다는 사실만으로 멈추거나 세션을 바꾸지 않는다(측정 기록이 없으면 `null`). 세션 신원·현재 권한·작업 계약 검증은 그대로 한다. 실제 세션 유실·문맥 초과는 아래 "세션 복구" 절차가 다룬다.

CLI의 직접 조회 도구도 닫는다. Claude는 빈 tools 목록과 빈 MCP 설정을 사용한다. Codex는 셸, 이미지 읽기, 웹, 앱·브라우저·컴퓨터 도구, 플러그인과 하위 에이전트를 비활성화한다. 필수 프로젝트 지시문은 서버가 넣는다. 이미지 첨부는 서버가 확인한 근거 이미지 한 장만 별도 입력으로 전달한다.

이미 읽은 타임라인 조각은 다음 단계의 문서 목록에서 빠져도 인용할 수 있다. 같은 세션·주제·작업 범위에서 전달을 인정한 기록이 있고, 해당 이벤트의 원문 해시와 조각 ID가 지금도 일치해야 한다. 취소된 호출이나 다른 세션·주제·범위의 기록은 이어받지 않는다. 이 대조를 위해 과거 원문을 모델에 다시 보내거나 현재 시도의 문서 목록 해시를 바꾸지 않는다.

### 위키 추가 검색(E3-5)

처음 고른 메모리 문서(라우터와 관련도로 고른 최대 네 문서)는 지금처럼 `memory:<경로>`로 매니페스트와 `sourceHash`에 고정한다. 바뀌면 기존대로 "Sources changed"로 초기화한다. 이 목록에 답이 없으면 허용 색인에서 다른 위키 문서를 찾는다.

- 허용 색인 `memory:@allowed-index`: 실행마다 만든다. 라우터·`MEMORY.md`의 링크 대상 가운데 이 역할이 읽을 수 있는 문서 전부를 한 줄에 하나씩 JSON(`path`·`version`·`bytes`·`context`)으로 적는다(`ProjectMemoryReader.index`, `memory-retrieval.md`). `version`은 가린 본문의 SHA-256이며 그 문서 조각의 `hash`와 같다. selector 는 `.md`가 아니라 실제 위키 경로와 겹치지 않는다.
- 싣는 자리: 색인과, 처음 고른 목록 밖 문서의 가린 본문은 매니페스트·`sourceHash`를 계산한 **뒤**에 싣는다. 그래서 읽지 않은 위키 문서의 편집은 시도를 초기화하지 않는다. 매니페스트(`context:manifest`)에 없으므로 과제 안내 한 줄이 색인 selector 와 크기를 알린다(메모리 디렉터리와 읽을 문서가 있을 때만). 처음 고른 문서는 매니페스트가 고정한 본문을 덮지 않고, 색인 줄의 버전도 그 본문의 것이다.
- 검색과 조회: 새 읽기 종류·스키마·골든 변경은 없다. 모델은 색인을 기존 `kind=memory` 조각(offset/nextOffset)으로 읽고 후보를 고른 뒤, `kind=memory selector=<경로>`로 청해 같은 조각 계약(전달·재전송 생략·채택·인용)으로 받는다.
- 색인은 읽음이 아니다: 색인 조각은 대상 문서를 읽은 것으로 치지 않는다. 색인의 버전으로 대상 조각 id 를 계산해 인용해도 전달된 적 없는 조각이라 거절된다. 대상의 버전 기록도 남지 않는다.
- 역할 밖 문서는 색인에 오르지 않고, 청해도 "Requested source is not in the pinned manifest."로 멈춘다.

버전 대조: 처음 고른 목록 밖 문서의 조각을 체크포인트에 실으면 그 버전을 `memoryReads{경로: 버전}`에 적는다. 같은 세션이 받은 조각을 상속 재검증이 전달로 되살릴 때도 적는다. 색인 문서는 적지 않는다(무관한 위키 편집마다 버전이 바뀐다).

- 적는 때: 호출이 반환된 뒤가 아니라 조각을 실을 때다. 호출이 끊겨 전달 기록 없이 남은 대기 조각도 다음 실행이 그대로 보내므로 같은 대조를 받아야 한다.
- 실행 시작: 적힌 버전이 지금과 다르면(본문 변경·링크 제거·읽을 수 없음·메모리 디렉터리 없음) 처음 고른 문서가 바뀐 경우와 같이 원문 변경으로 초기화한다. 사실·조각·전달·보존 응답을 채택하지 않고 "Sources changed"로 다시 판단한다. 논리 시도·사용량·회차는 보존한다. 초기화가 `memoryReads`도 지운다.
- 실행 중: 현재성 검사가 적힌 버전을 지금 원문과 대조해 "A wiki document read from the allowed index changed during planning."으로 멈춘다. 다음 실행이 위 초기화를 한다.
- 이 기록이 필요한 이유: 상속 조각 재검증은 바뀐 문서의 옛 조각을 전달 목록에서 지우지 않는다. 기록이 없으면 옛 본문에 기댄 사실·완료 응답이 그대로 채택된다.
- 한 실행 안의 본문은 실행 시작 때 고정한다. 조각 캐시 키에 그 본문 버전을 넣는다. 트리·`sourceHash`가 같아도 바뀐 본문의 옛 조각을 돌려주지 않는다(초기화 뒤 다시 청한 같은 selector·offset 이 새 판으로 실린다). 나머지 캐시 키는 그대로다.
- 읽지 않은 문서가 바뀌면 다음 실행의 색인이 새 버전을 싣는다. 색인 조각 id 가 바뀌므로 다시 청하면 재전송 생략 없이 실린다.
- 계보 진척은 원본별(`[kind, selector, hash]`)이라 색인과 대상 문서를 따로 센다.

## 중단과 재개

첫 호출 전과 유효 응답마다 SQLite에 중간 결과를 저장한다. 작업 범위, 계획 세대, 단계, Git 트리, 외부 근거, 선택한 메모리, 지시문 해시를 결속한다. 허용 색인으로 읽은 위키 문서는 전체 목록이 아니라 실은 문서의 버전(`memoryReads`)만 결속한다(E3-5). 현재 작업 트리의 미커밋 변경도 임시 Git index로 스냅샷에 포함하며 실제 index는 변경하지 않는다.

같은 계획 시도의 모든 조사 호출은 하나의 재작성·리뷰 예약을 공유한다. 재시작과 재시도는 이미 사용한 토큰·시간과 회차 수(측정값)를 유지한다. 자료가 바뀌면 이전 중간 결과를 보관하고 사실 판단을 무효화한 뒤 새 자료로 확인한다. 같은 범위에 새 사용자 결정·근거가 추가되면 다음 재시도에 입력과 순번을 갱신하고 다시 판단한다. 변경 전에 받은 응답을 그대로 확정하지 않는다. 같은 Claude 세션 ID와 전달한 작업 지시 해시를 보관하며, 서버 재시작 뒤에도 승인 계획과 연결된 세션을 구현에서 재개한다. 요청 수·비용·입력 바이트도 호출별 차이만 합산한다.

기본 정책은 `{ "mode": "observe" }`이며 토큰·시간 상한 없이 사용량만 기록한다. 한도가 없는 경우 예산 때문에 강제 정리를 요청하지 않는다. 기존에 설정한 숫자 한도는 명시적인 정책 변경 전까지 유지한다.

숫자 예산을 지정한 작업에서 실행 또는 전체 예산의 입력·출력·시간 중 하나라도 80%에 도달하면 추가 자료 조회를 멈춘다. 관측한 가장 큰 호출의 125%만큼 여유가 있을 때만 최종 정리를 시도하며, 실제 상한은 기존 예산 원장이 계속 집행한다. 이 여유 계산은 다음 호출 비용을 보장하는 예측값이 아니다. 최종 정리를 부르는 것은 이 soft limit 과 인용 교정뿐이다 — 조사 회차 수만으로 "No more research" 정리를 강제하지 않고, 마지막 조사 회차가 청한 읽기도 soft limit 전이면 제공한다(E3-4a, 예전 고정 회차 8 + 정리 1 은 제거했다).
예산이 강제한 정리가 완료 계획을 내지 못하면(`Synthesis did not produce a complete plan`) 정리 응답이 남긴 읽기를 체크포인트에 둔다. 예산을 늘리지 않은 재시도는 모델을 부르지 않고 예산 정지로 멈추고, 예산을 늘려 soft limit 이 풀린 재시도는 같은 시도에서 그 읽기부터 잇는다.
정리 응답이 완료 결과 없이 사용자 결정만 청해도 같은 경우다 — 정리 모드는 조사를 막아 모델이 읽을 곳을 요청이 아니라 결정 문장·질문으로만 남긴다. 체크포인트를 닫지 않고 열린 결정(`synthesisIncomplete`)으로 둔다(아래 결정 체크포인트). 결정 없는 재시도는 저장된 질문을 돌려주고, 결정 뒤 예산이 그대로면 모델을 부르지 않고 예산 정지로, 증액하면 같은 체크포인트(같은 admission·계획 epoch·조사 회차)에서 조사를 잇는다. 계획·개정·감사·종결 모두 같은 단계로 재개하고 재작성·리뷰 예약을 새로 쓰지 않는다. 응답을 저장한 뒤 채택 전에 끊긴 재생도 응답과 함께 저장한 출처(`responseFromSynthesis`)로 같은 판정을 받는다. 완료 결과와 함께 청한 결정과, 정리 밖의 읽기 없는 결정 요청은 종전대로 최종 결과다. 인용 교정 호출의 응답도 이 판정에 들지 않는다 — 인용 교정은 조사를 다시 열지 않는 한 번의 교정이라(증액 뒤에도 같다) 결정만 청해도 종전대로 최종이다. 한 시도는 예산 강제 정리를 한 번만 산다(`finalAttempted`): 증액 뒤 이어 간 조사가 새 한도에서 다시 soft limit 에 닿으면 정리 없이 예산 정지로 멈추고, 그 뒤는 모델이 조사 회차에서 스스로 완료하거나 중재 결정·증액으로 잇는다. 정리가 읽기를 남긴 경우와 같은 규칙이다. (E5 파일럿 51b22146 — 닫았을 때 계획은 새 epoch 재계획·재작성 1회 소비로 시도별 조사 누적·soft limit 기준이 초기화됐고, 감사·종결은 개정으로 내려갔다.)

두 회차 연속 새 근거나 해소된 질문이 없거나, 사용량이 누락되면 중간 결과를 보존하고 멈춘다. 사용량 누락은 재시도로 0으로 취급하지 않는다. 해당 시도의 예산과 세션을 중재자가 확인해야 한다. 원문 응답도 보존하며 형식 오류·남은 질문이 있는 결과는 최종 계획으로 승인하지 않는다. 계약 교정이 서버 제어 조사와 한도를 우회하는 별도 호출로 빠지지 않는다.

잘못된 UTF-8 읽기 위치는 요청별 오류로 다음 모델 호출에 돌려준다. 정상적으로 읽은 조각과 오류 설명을 함께 저장하므로 호출이 끊겨도 같은 체크포인트에서 요청을 고칠 수 있다. 오류는 근거·읽음 표시·진척으로 세지 않으며 반복하면 기존 두 회차 무진척 제한으로 멈춘다. 고친 요청으로 새 조각을 준비했다면 그 조각을 받아 판단할 호출은 허용한다. 결정 뒤로 미룬 읽기는 모델이 같은 원문의 위치를 고쳐 요청하고 그 조각을 실제로 받아 채택할 때까지 남긴다. 허용 경로·자격증명·고정 스냅샷 검증 실패는 계속 즉시 중단한다.

완료 응답의 강등(E3-4a Q-A·Q-A2, host-review 39d21df9 F002): `complete=true` 인데 읽기 요청이 남았거나, 아직 채택되지 않은 이연 읽기가 남았거나, 이 세션에 제시한 필수 타임라인 참조를 끝까지 읽지 않았으면 거절하지 않는다. 원문 응답은 `lastResponse` 에 그대로 두고 `complete=false` 인 중간 단계로만 채택해(`demotedComplete {requests, unreadRequired, deferred}`), 같은 시도에서 청한 읽기·남은 이연 읽기·남은 필수 구간(참조마다 이 세션이 빈틈없이 인정받은 끝부터, 호스트가 청함)을 제공한 뒤 다시 판단하게 한다. 완료 승인·최종 산출물은 만들지 않는다. 강등 자체는 진척이 아니다 — 새로 인정된 조각·사실·해소 질문만 진척이라, 새 근거 없이 되풀이한 완료는 위의 두 회차 무진척 규칙으로 멈춘다. 강등한 응답은 거절된 최종 응답이 아니므로 그 원문에 남은 미전달 인용으로 인용 교정을 열지 않는다. 남은 질문이 있는 완료(읽기 없음)는 지금처럼 승인하지 않고 멈춘다.

결정 뒤 이연 읽기(E3-4a Q-C): 사용자 결정을 청하면서 읽기를 남긴 응답은 그 읽기를 요청 당시 고정 스냅숏의 원문 버전(원문 전체 해시, 읽을 수 없었으면 null)과 재읽기 사유(`rereadReason`)와 함께 `deferredReads` 로 영속한다. 결정 뒤 첫 호출 전에 지금 고정 스냅숏에서 selector 와 버전을 다시 대조한다. 버전이 같으면 요청 offset 그대로, 바뀌었으면 예전 offset 을 조용히 쓰지 않고 첫 구간(0)부터 다시 읽으며 `deferredReadChanged {kind, selector, from, to}` 를 남긴다. 없어진 원문은 싣지 않고 전달·인정에도 넣지 않으며 `deferredReadMissing` 을 남긴다. 이전 읽음 표시(전달·인정 구간)를 새 세션에 복사하지 않는다(3a·3b 계약).

이연 읽기의 수명(host-review 39d21df9 F001·F002·F005·F006): 이연 읽기는 실제로 전달·채택되기 전에는 사라지지 않고, 남아 있으면 완료와 저장 본문 재사용을 막는다.

- 보존: 싣는 것만으로는 지우지 않는다. 그 조각(같은 kind·selector·offset·버전)이 실린 호출의 응답이 채택될 때 지운다. 호출이 실패·중단되면 대기 조각과 함께 요청이 남는다. 그 사이 원문이나 사용자 입력이 바뀌어 원문 변경 초기화가 대기 조각을 비워도 요청은 남아, 다음 실행이 지금 버전으로 다시 대조해 싣는다. 대기 조각을 들고 그대로 재개하면 그 조각을 보내고 채택 때 지운다(이중 제공 없음).
- 충족으로 지우는 경우: 이 세션이 이미 받은 조각이라 싣지 않은 것(재읽기 사유 없음)만 싣는 시점에 지운다. 재읽기 사유가 있으면 이미 받은 조각이어도 다시 싣는다 — 압축으로 잃은 문맥의 명시적 복구다.
- 완료 차단: 묶음 한도(24 KiB)로 한 회차에 다 싣지 못해 남은 이연 읽기가 있으면 `complete=true` 도 위 강등 규칙으로 중간 단계가 되고, 남은 묶음을 실은 뒤 다시 판단한다. 예산이 강제한 정리에서도 남은 이연 읽기가 있으면 완료로 채택하지 않고 `Synthesis did not produce a complete plan` 으로 멈춘다. 예산을 늘린 재시도가 남은 읽기부터 잇는다.
- 결정 체크포인트는 닫지 않는다: 결정을 청하며 읽기를 남긴 응답(이연 읽기, 또는 필수 참조 미완독 — F003)과 예산이 강제한 정리가 완료 결과 없이 결정만 청한 응답(`synthesisIncomplete` — 위)은 질문으로 돌려주되 체크포인트를 닫지 않는다(`awaitingDecision`). 세 원인은 한 경로다.
  - 새 사용자 입력이나 원문 변경 전까지 같은 시도를 다시 부르면 저장된 질문을 그대로 돌려준다. 모델을 부르지 않고 읽기도 싣지 않는다.
  - 결정이 오면 원문 변경 초기화가 표식과 단계를 비우고, 같은 체크포인트(같은 admission·계획 epoch·조사 회차 누적)가 이연 읽기와 남은 필수 구간을 실은 뒤 다음 응답으로 계획·개정을 낸다. 재작성 예약을 새로 쓰지 않는다. 예산 강제 정리의 열린 결정이면 soft limit 이 풀리지 않은 재개는 정리를 다시 사지 않고(`finalAttempted` — 한 시도에 한 번) 예산 정지로 멈춘다.
  - 계약 위반으로 무효화된 결정 응답은 재생하지 않는다(F008). 엔진의 과제 계약 검사(`enforceResultContract` — 응답 종류·앞 단계 지적 승계)가 결정 응답을 거절하면, 같은 체크포인트를 교정 대기(교정 질문을 앞에 둔 미완료)로 되돌리며 `awaitingDecision` 도 내린다.
    - 새 입력 없는 공개 retry 는 저장된 질문 대신 교정 질문을 실은 모델 호출에 닿는다. 같은 admission·세션을 이어 재작성·리뷰 예약을 새로 쓰지 않는다.
    - 이연 읽기는 지우지 않아, 교정 호출에 버전을 다시 대조해 실린다.
    - 무효화 상태는 무효화 지점 한 곳이 정하고, 재생 분기에는 예외를 두지 않는다.
- 저장 본문 재사용 차단과 같은 단계 재개: 판정은 엔진의 `openReadObligation(stage)` 하나다. 모두 만족할 때만 참이다.
  - 가장 최근 체크포인트가 그 단계의 미확정 체크포인트이고 열린 질문 표식이 있다.
  - 이연 읽기나 필수 미완독이 남았거나, 예산이 강제한 정리가 완료 결과 없이 결정만 청했다(`synthesisIncomplete`).
  - 범위 세대·계획 epoch·계획 SHA 가 지금 주제와 같다.
  - 공급자·바인딩이 그 단계를 재개할 **실제 job route**(계획 planner/plan, 개정 planner/revision, 감사 reviewer/audit, 종결 reviewer/closeout)와 같다. guardedPlanning 이 체크포인트를 잇는 기준(`ownedByTurn`)과 같은 식이다.
    - 좌석 표에 남은 바인딩은 정본이 아니다. 계획·개정을 같은 공급자의 다른 참여자로 배정하면, 개정은 새 세션이라 좌석을 갱신하지 않는다.
    - route 는 부작용 없는 `resolveRoute` 로 푼다. 풀 수 없는 배정이면 의무가 남아 있으므로 참이다 — 그 단계로 재개하고, 실제 턴의 경로 판정이 거부 사유를 남긴 채 멈춘다(모델 호출 없음). 요청한 자료를 조용히 버리지 않는다.
  이 판정을 쓰는 곳은 다음과 같다.
  - 계획·개정: 멈춘 결과 재사용(`pausedPlanReusable`·`pausedRevisionReusable`)이 이 판정이 참이면 결정 응답에 실린 본문을 채택하지 않는다. 공개 retry 는 계획이면 미완료 체크포인트 분기, 개정이면 개정 재개로 같은 체크포인트를 잇는다.
  - 감사·종결(F007): 결정을 청하며 읽기 의무를 남긴 감사·종결 결과는 확정 결과가 아니다.
    - 생산자가 먼저 그 단계에서 멈춘다(재개 단계 CODEX_AUDIT·CODEX_CLOSEOUT). 감사는 결과를 소비하기 전의 결정 멈춤이 이미 그렇다. 종결은 이 판정으로 멈추며, 후속 목록·구현 노트 기록, 필수 쟁점 분류(개정 2회차·추가 개정 결정), 처분 되돌림·합의 판정보다 앞선다.
    - 전이표는 결정 멈춤에서 감사·종결로 가는 길을 막는다(결정을 소비하는 단계는 개정). 그래서 이 판정이 참일 때만 공개 retry 가 예산 정지와 같은 FAILED 경유로 그 단계를 재개한다.
    - 재개된 턴은 같은 체크포인트(같은 admission·세션·epoch)를 이어 대기 읽기를 싣는다. 그 뒤 나온 완료 결과는 종전대로 판정·분류돼 다음 단계(감사 → 개정, 종결 → 개정 2회차·추가 개정 또는 합의 확인)로 간다. 완료된 종결의 처분·REPLAN·회귀 판정 의미는 그대로다.
    - 결정 없이 retry 하면 저장된 질문을 돌려주고 다시 멈춘다.
  - 의무가 없는 일반 결정 멈춤과, 멈춘 사이 그 job 이 다른 참여자로 재배정된 경우는 종전대로 개정이 결정을 소비한다(재배정되면 guardedPlanning 이 옛 대화를 잇지 않는다).
  - 계약 위반 무효화(F008)는 표식을 내리지만 `planningPause` 로 멈춘다. 그래서 retry 는 첫 분기(예산·계획 정지)의 FAILED 경유로 같은 단계를 재개한다.
  - 개정 2회차·추가 개정(F009): 결정을 청하며 읽기를 남긴 개정은 아직 채택되지 않은 결과다.
    - 사용자 결정 뒤 재개는 바퀴 합의·종결 판정보다 먼저 같은 개정 턴을 다시 연다. 쟁점은 저장된 종결과 채택된 개정 집합에서 고른다(그 개정을 열 때와 같은 입력). 쟁점이 비면 합의로 넘어가지 않고 멈춘다.
    - 같은 체크포인트(같은 admission·세션·route·epoch)가 대기 읽기를 싣는다. 개정을 채택(새 계획 저장)하고 새 계획 SHA 로 종결 확인을 한 뒤에야 합의로 간다.
    - 호출이 실패해도 의무가 남아, 다음 재시도가 같은 체크포인트에서 잇는다.
- 바퀴 합의(`roundKnownFindings` — 종결 판정·재개 정보·되돌림 가드의 기준 집합)는 **채택 기록이 있는 개정만** 모은다(F009·F010). 채택 판정에 쓰는 증거는 셋이고, 채택은 마지막 하나뿐이다.
  - 수신: 개정 결과 산출물(`claude-revision`)이 저장됐다는 것은 엔진이 유효한 결과를 받았다는 뜻일 뿐, 계획과 연결되지 않는다. 채택이 아니다. 복구 후보 판정에만 쓴다.
  - 산출물 저장: 개정 계획의 plan 산출물 행이 있어도, 주제는 옛 계획을 가리키고 ACK 도 그대로일 수 있다(실패한 저장의 잔재). 채택이 아니다. `savePlan` 이 같은 판으로 재사용하는 데만 쓴다.
  - 계획 확정: 그 결과 산출물을 가리키는 계획 확정 이벤트(`payload.adoptedResult`)다. 이것만 채택이다. 계획을 유지하는 엔진 합성 개정(경미 지적만의 감사 뒤)은 엔진이 쓰는 생략 이벤트(`skippedRevision`)의 `adoptedResult` 가 채택 기록이다. 응답 내용·요약으로 추정하지 않고, 사용자 이벤트는 세지 않는다.
  - 멈춘 채 대체된 개정과 질문 재생 사본은 채택 기록이 없으므로 쟁점을 처리한 것으로 세지 않는다. 결정 뒤 본문을 재사용해 계획을 확정하면 그때 기록이 생긴다.
  - 계획 SHA 로는 가르지 않는다. 개정 결과는 계획 SHA 를 담지 않고, 합성 개정은 계획을 바꾸지 않는다.
- 계획 저장(`savePlan`)의 확정 경계(F010)
  - 순서: 산출물 쓰기 → 현재성 검사 → 계획 세션 바인딩 → 확정. 확정은 계획 필드·승인 무효화·ACK 삭제·확정 이벤트를 한 transaction 으로 쓴다.
  - 그래서 "계획 SHA 는 새것인데 채택 기록이 없는" 상태와 "확정됐는데 바인딩이 없는" 상태가 생기지 않는다. 바인딩은 계획 SHA 가 같을 때만 읽히므로 확정 전 바인딩은 효력이 없다.
  - 산출물까지만 쓰고 끊긴 저장을 다시 부르면, 최신 plan 산출물이 같은 본문이고 계획 SHA 가 아직 그것이 아닐 때 그 산출물을 같은 판으로 받는다(다시 쓰지 않음).
- 받았지만 확정하지 못한 개정의 복구(F010): 개정 재개는 바퀴 합의·쟁점 선택·개정 재실행보다 먼저, 이 바퀴의 가장 최근 계획 제어 결과이면서 채택 기록이 없고 멈춤을 요청하지 않은 개정을 찾는다.
  - 찾으면 모델 재호출이나 새 예약 없이, 확정된 계획 위에 한 번 적용해 확정하고 새 SHA 로 종결 확인을 한다.
  - 재개 바탕(`storedPlanForResume`)은 확정 SHA 에 결속한 계획이다(`requireCurrentPlanArtifact`). 최신 산출물이 아니므로 편집이 두 번 적용되지 않는다.
  - 이미 채택된 개정은 결정 뒤 재사용 대상이 아니다.
  - 복구 적용에는 바탕 증명이 필요하다(F011).
    - 그 개정 뒤에 계획 확정(모양 무관)이 없어야 한다.
    - 그 개정 앞 마지막 확정의 SHA 가 지금 계획 SHA 와 같아야 한다.
    - 어긋나면 적용하지 않고 확정된 계획을 바탕으로 개정을 다시 돌린다. 편집을 다시 적용하지 않는다.
- 이전 버전 이력의 채택(F011): 채택 판정은 `adoptedRevisions` 한 곳이다. `adoptedResult` 가 없는 이전 버전(860d8cb 이하) 기록은 그 생산자의 모양과 순서로만 읽는다. 기존 기록은 고쳐 쓰지 않는다(읽기 쪽 호환).
  - 구형 계획 확정(payload 필드가 정확히 `{artifactKind, revision, artifactRevision, sha256}`)은 같은 세대에서 그 앞의 가장 최근 결과 산출물(계획·개정)에 결속한다. 다음을 모두 만족해야 채택이다.
    - 그 결과가 개정이다.
    - 결과와 확정 사이에 감사·종결이 없다.
    - 수신 기록이 있다.
    - 멈춘 결과라면, 받은 뒤 사용자 결정이 있다.
    계획 1판의 확정은 어떤 개정도 채택하지 않는다.
  - 구형 합성(system/system, payload 필드가 정확히 `{skippedRevision, implementationNoteIDs}`)의 생략 이벤트 S 는 S 이하의 가장 최근 결과 P 에 결속한다. 다음을 모두 만족해야 채택이다.
    - S 가 생산자의 단계(`CODEX_AUDIT`)에서 남았다.
    - P 가 개정이고, 같은 순번의 결과가 둘이 아니다.
    - P 와 S 사이(P 의 순번 포함)에 감사·종결 산출물이 없다.
    - 그 사이에 결과 수신·확정 기록(`agent_output`)이 없다.
    그 사이의 다른 사건(사용자 입력·설정 변경·원문 변경·역할 배정·위임 호출 기록·검사 지표)은 S 가 어느 결과를 가리키는지와 무관하므로 가리지 않는다.
    근거: 생산자(4f086bf~860d8cb 판마다 같다)는 감사 단계에서 revision 을 정하고, accept(취소 아님·같은 실행·같은 범위 세대·같은 상태)를 통과한 저장 뒤 곧바로 S 를 남긴다. 주제당 실행은 하나라 그 사이에 다른 결과가 저장·수신되지 않는다.
    그 사이 기록의 state 는 단계 증거로 쓰지 않는다. 검사 완료 지표는 await 전에 읽은 state 를 싣고(`verifications.ts:132→147`), 그 사이의 실제 단계·세대 변경(중단·범위 변경)은 accept 가 합성 산출물을 버려 S 자체가 생기지 않는다(F011 7차).
  - 진단 계획 개정 확정(`diagnosisPlanRevised` 가 더 붙음), 다른 세대, 순서를 증명할 수 없는 동률은 채택하지 않는다.
  - 근거: 결과 산출물 revision 은 저장 시점의 타임라인 순번(다음 이벤트의 sequence)이고, 타임라인 행은 지우지 않는다.
- 예전 설계(결정 체크포인트를 닫고 새 시도가 이연 읽기를 상속)는 없앴다. 계획은 재사용을 막으면 재계획(`restartPlanning`)으로 가 계획 epoch 가 올라 상속 조건이 깨지고, 닫힌 체크포인트 뒤 새 프롬프트는 새 admission 이라 재작성 예약을 새로 썼다.

## 검증과 지표 해석

공개 워크플로 재시도, 중간 결과 복구, 예산 경계, 자료 변경, UTF-8 조각 재구성, 경로 이탈·인증 파일 배제, 불완전한 계획 차단을 테스트한다. 어댑터 테스트는 최종 입력 크기와 도구 설정, 이미지 전송을 검사한다.

2026-09-23에 설치된 Codex CLI `0.155.0-alpha.9`와 Claude Code `2.1.280`을 임시 홈과 로컬 모의 API에 연결했다. 서버가 받은 요청에서 Codex는 도구 목록이 없었고 Claude는 빈 목록을 보냈다. Claude 이미지 입력도 같은 로컬 경로에서 파싱됐다. 모의 API가 의도적으로 요청을 거절했으며 실제 모델 사용량이나 계획 품질을 측정한 실험은 아니다. CLI 업데이트 뒤에는 이 경계를 다시 확인해야 한다. Claude의 계획→구현 재개 시 모델·ultracode·도구 권한 전환은 어댑터 명령 계약으로 검사하며, 실제 모델의 문맥 보존 품질은 별도 파일럿에서 확인해야 한다.

화면은 누적 입력·캐시 읽기·호스트 텍스트 바이트·관측된 요청별 최대 입력을 구분한다. 요청별 입력을 제공하지 않는 CLI는 `측정값 없음`으로 표시한다. 누적 입력을 한 번의 문맥 크기나 과금액으로 해석하지 않으며, 입력 바이트 감소를 실제 토큰 절감률로 보고하지 않는다. 실사용 파일럿이 끝나기 전에는 기본 적용이나 비용 개선이 검증됐다고 보지 않는다.

Claude의 누적 문맥에는 CLI의 기존 자동 압축 설정을 적용한다(계획 800,000 / 구현 600,000). 이는 계획·개정 턴의 호스트 입력 64 KiB 제한이나 측정된 요청별 토큰 수와 다른 설정이며, 세션 ID 유지가 모든 대화 원문의 영구 보존을 뜻하지 않는다. Codex 검토의 턴당 입력은 96 KiB까지 허용한다. 같은 세션의 누적 호스트 입력·응답은 측정값일 뿐 공급자의 실제 문맥 상태가 아니므로 호출을 막는 기준으로 쓰지 않는다(E3-3a 에서 예전 감사 256 KiB·종결 384 KiB 정지, 누적 기준 세션 교체, 누적 조건의 축약 최종 정리를 없앴다).

## 세션 복구(E3-3a 검토자 좌석, E3-3b 작업·리뷰·연속성 작성자 좌석)

복구 순서는 계획 §3.6 을 따른다: 현재 세션 정상 재개 → 확인된 공급자 압축 → 체크포인트 확정 → 같은 실행 도구·모델·옵션의 새 세션 → 인계.

- 복구 사유는 어댑터가 올린 실패 코드뿐이다. 관측된 형태만 코드가 된다.
  - Claude 세션 유실: stderr "No conversation found with session ID" 와 모델 호출 없는 result 이벤트.
  - Codex 세션 유실: stdout 없이 "thread/resume failed: no rollout found for thread id".
  - Codex 문맥 초과: 오류 message "Codex ran out of room in the model's context window".
  - 그 밖의 실패는 `unknown` 이다. 복구하지 않고 원형을 보존해 멈춘다. Claude 문맥 초과 형태는 관측이 없어 아직 `unknown` 이다.
- 사용량이 빠진 실패 뒤에는 복구 호출을 사지 않는다. 다음 모델 호출 전에 멈추는 기존 사용량 누락 정책이 복구보다 앞선다.
  - 실제 Codex 문맥 초과처럼 토큰 사용량 없이 끝난 호출이 이 경우다.
  - 예외: 모델 턴이 없음을 관측한 세션 유실은 사용량 누락으로 세지 않아 그대로 복구한다.
- 공급자 압축: 호스트가 호출 단위로 부를 수 있는 압축은 두 공급자 모두 없다. Claude 는 CLI 자동 압축만 적용 중이다. 복구 기록에 `automatic-only`·`unsupported` 로 남기고 새 세션으로 인계한다. 합성 프롬프트를 줄이는 것은 공급자 압축이 아니다.
- 인계
  - 보존: 과제(전체 판)·결정·미해결 지적·체크포인트·승인·사용량·회차.
  - 상속하지 않음: 옛 세션의 읽음 표시(전달 조각, 계약·지시문 전달, 타임라인 인정 구간). 새 세션이 처음부터 받는다.
  - 공급자·모델은 바꾸지 않는다.
  - 대화 측정값은 세션별로 나눈다.
    - 떠나는 세션의 입력·응답 바이트와 실행 여부는 체크포인트의 `sessionMeasurements` 에 남아, 그 세션의 문맥 측정이 계속 읽는다.
    - 새 세션의 회차·바이트는 0 부터 센다. 옛 세션의 측정값(`context`)은 지운다.
    - 시도 단위 합(조사 한도·예산 환급·진행 표시)은 재배정의 대화 분리와 같은 `priorAttempt` 로 이어받는다.
- 복구 계보: 자동 복구 1회는 좌석의 계보 단위로 센다.
  - 새 계보는 엔진이 그 좌석의 결과를 검증·채택해 새 산출물(검토자 `audit`·`closeout`, 계획자 `claude-plan`·`diagnosis-plan-revision`·`claude-revision`)이 생긴 경계에서만 열린다.
  - 다음은 계보를 바꾸지 않는다: 계획 SHA·epoch·범위 세대 변화, 재키, 오류 사유 변경, retry, DB 다시 열기. 계약 좌표는 기록에 현재 계약 정보로만 남는다.
- 유효 진척: 계보에 이미 자동 복구가 있으면, 그 뒤 계보의 모든 세션에서 **인정된** 원문 구간 합집합이 늘었을 때만 한 번 더 복구한다.
  - 이 합집합은 세션별 전달 영수증과 따로 계산하고, 범위 세대는 원본 신원에 넣지 않는다.
  - 출처는 두 인정 기록뿐이다.
    - 타임라인 참조: 전달 인정 기록(반환·현재성 재대조 뒤). 계획 제어 읽기와 호스트가 실은 쪽이 같은 신원으로 적는다. 같은 원문을 조각으로도 받지만, 그 조각은 따로 세지 않는다.
    - 파일·근거 조각: 현재성 검사와 단계 채택을 통과한 호출의 조각만 센다. 반환 직후 적는 전달 기록만 있는 조각은 세지 않는다.
  - 진척이 아닌 것
    - 같은 구간 재읽기·재완독(다른 경로로 다시 받은 것 포함)
    - 현재성·채택이 거절된 호출의 조각
    - 문구만 다른 응답, 오류 응답 저장, 결정·증거 추가
  - 진척이 없으면 멈추고 다음을 남긴다: 두 사유, 세션, 원형 오류, 기준선.
- 복구·차단 기록의 실패는 공급자·코드·원형 출력을 함께 남긴다.
  - 원형 출력은 어댑터가 비밀을 가리고 끝부분만 자른 값이다. DB 를 다시 열어도 분류를 다시 대조할 수 있다.
  - 원문 전체를 저장하거나 가린 값을 되살리지 않는다.
- 예상 밖 세션 신원 변경은 응답을 채택하지 않는다(기존 차단).
  - 두 경로에서 온다. CLI 가 다른 세션 id 를 알린 경우, 그리고 Codex 어댑터가 재개 스트림의 다른 thread 를 구조화된 오류로 거부한 경우다.
  - 어느 쪽이든 복구 상태에 요청·반환 세션 id 를 남기고 멈춘다. 자동 복구 사유가 아니다.
- 세션 유실 판정은 어댑터가 관측으로 분류한 코드뿐이다(`isMissingSessionError` = `AgentRunError.code === "session-missing"`). 같은 문구를 담은 일반 오류는 유실이 아니다. `session-missing` 분류가 모델 턴 없음 관측을 필요조건으로 요구하므로 사용량 누락 예외도 이 코드로 판정한다.

### 좌석과 계보 경계(E3-3b)
- 계보는 좌석마다 따로다: 계획 제어 `planner`·`reviewer`(E3-3a), 구현·수정 공용 `implementer`, 코드 리뷰 `code-review`.
- 계획 제어 좌석의 경계는 엔진이 채택한 산출물이다(E3-3a).
- 작업·리뷰 좌석의 경계는 승인·수락 게이트를 통과한 상태 전이 이벤트에 실은 과제 짝 표식(`recoveryBoundary`)이다. 한 transaction 으로 기록되며, 표식 종류는 다음과 같다.
  - 승인 계획의 구현 시작(sha·epoch·세대)
  - 구현 수락(acceptId)
  - 수정 수락(acceptId·계약)
  - 진단 전용 계약 닫힘
  - 리뷰 채택(원본 리뷰 산출물)
  - 리뷰 통과(인도 대기)
- 좌석별로 받는 표식
  - `implementer`: 앞의 넷.
  - `code-review`: 리뷰 채택·통과와 작업 수락(새 리뷰 입력의 채택).
- 저장만 된 결과, 수락 중 새 입력으로 멈춘 수락, 거절된 수락, 표식 없는 전이(재시도의 `from: FAILED` 등)는 경계가 아니다. 같은 전이의 재사용·retry·재키·DB 다시 열기도 경계를 만들지 않는다.
- 경계가 바뀌어도 논리 작업의 사용량·회차·리뷰 예산은 그대로다.

### 작업·리뷰 좌석 복구(E3-3b)
- 구현·수정 작업 세션에 보낸 호출(첫 쓰기·계속 진행·완료 확인·허용 오차 교정)이 관측된 세션 유실·문맥 초과로 끝나면, 계보가 허가할 때만 같은 route 새 세션으로 같은 논리 작업을 다시 연다.
  - 대조하는 세션은 실패 시점에 그 실행이 쓰던 작업 세션이다(시작 세션, 또는 그 실행 안에서 만들어 저장한 세션). 같은 실행의 계속 진행·확인 턴에서 새 세션을 잃어도 재시도 없이 그 자리에서 판정한다.
  - 누적 checkpoint 와 열린 요청은 논리 작업에 그대로 있다. 새 세션은 전문 판과 처음부터의 타임라인 쪽을 받는다.
  - 허가되면 복구 기록이 먼저 남는다. 그 뒤 새 세션이 생기기 전에 끊겼으면 잃은 세션을 다시 부르지 않고, 새 복구도 쓰지 않은 채 그 복구를 잇는다.
- 코드 리뷰 세션에 보낸 호출(리뷰·답변 확인)이 같은 실패로 끝나면 `code-review` 계보로 새 리뷰 세션을 한 번 연다.
  - 이때 전문 판과 처음부터의 쪽을 보낸다.
  - 잃은 세션에서는 답변 확인을 하지 않는다.
  - 재개 경로가 리뷰 세션에 직접 보내는 답변 확인(리뷰·최종 리뷰 재개, 인도 대기 재확인)도 같은 판정을 지난다. 복구가 허가됐거나 대기 중이면 저장 리뷰 재사용이나 저장 리뷰로 수정 열기로 가지 않고 새 리뷰 세션으로 리뷰한다.
- 사용량 가드: 실패한 그 호출의 마지막 사용량 스냅숏이 완전해야 복구한다. 이전 성공 턴의 값을 쓰지 않는다.
  - 관측이 없으면 unknown 이고 0 으로 보지 않는다. 사용량은 기존 observer·원장에 그대로 기록된다.
  - 예외는 `session-missing` 이다.
- 유효 진척은 둘 중 하나다.
  - 계보 세션 전체의 참조 전달 인정 합집합 증가
  - (`implementer`) 기준선에서 열려 있던 요청이 같은 논리 작업의 검증 계열 checkpoint(verified·accepting·accepted)에서 닫힘
    - paused 는 세지 않는다. 허용 오차 교정 뒤 위반이 남은 정지는 검증을 통과하지 못한 누적본을 paused 로 남긴다. 검증된 정지는 같은 누적본의 verified 가 앞에 있어 그 해소는 그대로 센다.
    - 그 checkpoint 를 읽지 못하면(손상) 해소를 세지 않는다. 이때 차단 기록의 열린 요청은 `null` 이다(빈 목록 = 전부 해소와 구분한다).
- 진척이 아닌 것
  - 결정·증거 추가, 해소 이벤트, 원본 응답
  - 기준선 뒤 새 요청의 해소
  - 이미 반영된 해소의 재계산
- 복구하지 않으면 기존대로 멈춘다(연속성 작성자 좌석의 세션 유실은 결정 대기, 그 밖은 원래 오류).
- 비연속성 작업 좌석이 CLI 의 세션 id 변경을 받아들이는 기존 계약은 그대로다. Codex 재개 스트림의 다른 thread 는 해당 좌석 계보에 신원 불일치로 남는다.

### 연속성 정책 2 작성자 좌석(E3-3b)
- 계획·개정 턴: 계획 제어 래퍼의 복구를 세션 유지 계획자 좌석에도 적용한다. 실행기는 CLI 가 돌려준 새 세션 id 를 그 계보의 마지막 복구 기록(직전에 수용한 세션 → 새 id)과 짝일 때만 받는다. 짝이 없으면 채택하지 않고 기록한 뒤 멈춘다.
  - 새 세션은 영속 계보의 대기 중 복구에 잇는다(복구 허가와 새 세션 생성 사이에 끊겨도 같다). 좌석·계약 좌표(단계·범위 세대·epoch·계획 sha·바인딩)·원래 세션이 맞을 때만 잇는다.
  - 이을 때 구현 연결도 한 transaction 으로 옮긴다. 조건은 구현 세션이 그 복구의 원래 세션이고 구현 바인딩이 같을 때다. 그래서 구현한 주제의 계획 개정 중 복구해도 재승인 뒤 구현이 새 세션을 잇는다.
- 구현·수정 턴: 복구 세션 S1 에서 읽기 전용 확인을 마친 뒤에만 쓰기를 재개한다.
  - 확인 턴: 같은 작업 route(공급자·참여자·모델·설정·options 그대로)에 job `planner/ack` 를 붙인다. 도구가 없고 계획 제어도 붙지 않으며, 개정·리뷰 예약을 쓰지 않는다.
    - S1 을 만들며 기존 ACK 프롬프트로 승인 계획 sha 를 확인한다. 합의 단계의 격리 ACK 처럼 제3세션에서 확인하지 않는다.
  - 대조
    - 실행기: 취소·상태·범위 세대·근거·계획 epoch·sha·새 입력
    - 이 절차: 응답 종류(ACK)·승인 sha 일치·작성자 좌석과 작업 경로의 바인딩·다른 주제와의 세션 충돌
  - 통과하면 한 transaction 으로 S1 에 옮긴다: 참여자(ACK 는 S1 이 답한 값), 승인 바인딩(복구 원점·확인 결과를 담은 검증 기록), 구현 세션, 계보.
    - 기존 ACK 를 복사하지 않고 사용자 승인을 만들지 않는다. 계획자 finalized checkpoint 도 S1 이 쓴 것처럼 바꾸지 않는다.
  - 대조가 어긋나면 옮기지 않고 멈춘다. 확인 전에 끊겼으면 영속된 S1 을 이어 같은 확인을 마친다(새 세션·새 복구 없음).
  - 전환 뒤 첫 쓰기 턴은 전문 판이다.
- 재계획·재승인 뒤: 참여자가 S1 이므로 진단 계획 개정 턴이 S1 을 재개한다. S1 이 만든 계획자 checkpoint 로 기존 바인딩 절차가 S1 을 묶고, 구현이 S1 을 잇는다.
- 구현·수정의 필수 타임라인 읽기(E3-4b): 완료 보고 뒤 남은 필수 구간은 필수 읽기 턴으로 잇는다. 계속 진행 상한 4회는 러너 `in_progress` 에만 쓴다.
  필수 읽기 턴은 횟수 상한 대신 진척 게이트로 끊는다 — 턴 직전 필수 참조 집합과 작업 세션의 미인정 바이트를 고정하고, 턴 뒤 같은 집합·같은 세션에서 호스트 인정으로 줄지 않으면
  (예: 응답이 다른 세션 id 로 돌아옴) 결과·인정 구간을 보존하고 `readingStalled` 로 멈춘다. retry 는 같은 세션에서 잇는다.
- 코드 리뷰의 필수 타임라인 읽기(E3-4c): 리뷰 세션이 아직 받지 않은 필수 구간이 한 리뷰 호출의 쪽 예산(96 KiB)을 넘으면 판정 전에 리뷰 읽기 호출(`reviewer/review-read`, 도구 없음, 응답 ACK, 리뷰 경로의 모델·추론 설정 그대로)로 앞부분을 싣고, 남은 구간이 한 호출에 들면 마지막 판정 호출이 판정한다. 인정은 정상 반환·현재성 재대조 뒤 실은 쪽만이고, 반복은 4b 와 같은 진척 게이트가 끊는다(`readingStalled`, ACK 위반은 `reviewReadInvalid`). 논리 리뷰 한 번은 호스트 소유 원장 ID 하나(`planning_review_ledgers`)로 리뷰 1회를 예약하며, 원장의 첫 spawn 뒤에는 spawn 전 실패로도 예약을 되돌리지 않는다. 판정이 돌아오면 원장은 닫히고, 완료(완료 리뷰 + 전 구간 인정 + 같은 tree/계약)일 때만 리뷰 커서·저장 리뷰 재사용·저장 리뷰로 수정 열기를 허용한다. 세션 유실은 code-review 계보 복구로 같은 원장을 잇고 새 세션은 처음부터 읽는다.
